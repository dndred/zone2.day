# 05. Синхронизация и доставка

Цель: **«составил план в чате → вышел на улицу → план уже в телефоне и в часах»**, без кнопки «обновить» и без сети в момент тренировки.

## 1. Модель

- **Сервер — источник истины** для плана, профиля, стартов, активностей.
- **Телефон — источник истины** для дампов HealthKit и логов зала до момента их отправки.
- Писатели почти не пересекаются: план пишет только AI, лог зала — только приложение, AI правит его лишь изредка. Поэтому CRDT не нужен: правило «последняя запись побеждает» по каждой записи подхода плюс идемпотентность.

## 2. Pull: лента изменений

```
GET /v1/sync?cursor=<seq>&limit=500
→ 200 {
    "changes": [
      { "seq": 1042, "entity": "planned_workout", "id": "…", "op": "upsert", "version": 7, "data": { … } },
      { "seq": 1043, "entity": "planned_workout", "id": "…", "op": "delete" }
    ],
    "cursor": "1043",
    "hasMore": false,
    "snapshot": false,
    "serverTime": "2026-11-15T18:02:11Z"
  }
```
- Сущности ленты: `profile`, `week`, `planned_workout` (с `resolved` и `last_change`), `event`, `activity` (сводка, интервалы, связь с планом; без рядов), `strength_session`/`strength_set`, `daily_metrics` (агрегаты для UI), `journal`, `notebook_page` (база знаний офлайн), `gear`, `export_hint`.
- Лента хранит только «что изменилось» (`sync_feed`), данные читаются в момент запроса: несколько правок одной записи приходят одним текущим состоянием, удалённая запись — `op: delete`. Активности-дубли (копия Strava) для приложения тоже `delete`.
- `planned_workout` приходит с `resolved` — таргеты в абсолютных единицах по текущему профилю. Если в странице есть изменение профиля, сервер заново присылает все будущие тренировки (с сегодняшнего дня по TZ атлета), чтобы %-таргеты на часах обновились.
- Без курсора — снимок (`snapshot: true`), его `cursor` = голова ленты, взятая **до** чтения данных: всё, что записалось во время чтения, придёт в следующем инкременте ещё раз (применение идемпотентно).
- Ряды и файлы в ленту не входят: детальные ряды для графиков приложение подкачивает лениво (`GET /v1/activities/{id}/streams?maxPoints=…`) и кэширует.
- **Окно ленты для нового устройства:** снимок «−90 дней … +60 дней», затем инкрементально.
- Применение — одной транзакцией GRDB; UI обновляется через наблюдаемые запросы (`ValueObservation`).
- `410 Gone` на курсор, которого нет у этого пользователя (впереди головы ленты, например после пересоздания базы) → полный ресинк. Чистки старой ленты пока нет; когда появится, слишком старый курсор тоже получит 410.

## 3. Push вверх: outbox

Таблица `outbox` в GRDB: `id` (UUID — он же ключ идемпотентности), `kind`, `payload`/`fileRef`, `attempts`, `nextAttemptAt`, `lastError`.

| kind | Эндпоинт | Идемпотентность |
|---|---|---|
| `activity_upload` | `POST /v1/activities` (gzip-дамп; если больше 6 МБ — `POST /v1/uploads` → подписанная ссылка на прямую загрузку в Storage → `POST /v1/activities/commit`) | по `HKWorkout.uuid` |
| `daily_metrics` | `POST /v1/daily-metrics` (батч) | upsert по дате |
| `strength_sets` | `POST /v1/strength-logs` (батч) | по `set.id` (клиентский UUID) |
| `delivery` (✅) | `POST /v1/deliveries` — снимок «что на часах» + состояние синка устройства | один логический id `delivery-report`: новый отчёт заменяет неотправленный старый |
| `client_logs` | `POST /v1/client-logs` | по `batch.id` |
| `health_written` | `POST /v1/activities/{id}/health-export` | по `activity id` |
| `health_deleted` | `POST /v1/health-deletions` (батч UUID) | по `HKObject.uuid` |

Экспоненциальный backoff, отправка при любой активации приложения. Ошибки видны на экране Debug и в `debug_devices`.

## 4. Когда приложение синхронизируется

### Фаза 1 (бесплатная подпись, без push)
| Триггер | Механизм | Ожидаемая частота |
|---|---|---|
| Открытие приложения / возврат на передний план | `scenePhase == .active` | всегда, без кнопки |
| Свайп вниз (pull-to-refresh) | `.refreshable` на Today и Calendar | по желанию; привычный жест, не обязательный шаг |
| Фоновое обновление | `BGAppRefreshTask` (`earliestBeginDate` +30 мин, перепланируется после каждого запуска) | iOS решает сама; при ежедневном использовании — несколько раз в день |
| Новые данные в HealthKit | `HKObserverQuery` + `enableBackgroundDelivery` — для тренировок (`.immediate`), для шагов, пульса и сна (`.hourly`) | после каждой тренировки; примерно раз в час, пока часы пишут данные |
| Ночная обработка | `BGProcessingTask` (при зарядке и Wi-Fi) | тяжёлые отправки, полный ресинк |
| После завершения тренировки | срабатывание observer'а | сразу |

Каждая фоновая активация (от HealthKit, `BGAppRefreshTask` и т.д.) запускает **полный цикл**: pull → применить → пересчитать расписание часов → отправить outbox. Бюджет — около 25 секунд.

**Принятое ограничение фазы 1:** если план поставлен за несколько минут до выхода, приложение за это время ни разу не проснулось, а сети на улице нет — тренировки на часах не будет. На первом этапе это нормально; полностью закрывается push в фазе 3. AI об этом атлету не напоминает. Спайк S4 измеряет реальную частоту фоновых пробуждений.

### Фаза 3 (платный аккаунт, push)
| Канал | Механизм |
|---|---|
| Silent push (`content-available: 1`) | сервер шлёт после каждой мутации плана (с дебаунсом ~30 с), приложение просыпается и синкается |
| Видимый push «Plan updated» + **Notification Service Extension** | NSE срабатывает даже у принудительно закрытого приложения: тянет `/v1/sync` в общую базу (App Group), текст уведомления локализуется |
| Тихий push на часы (ф.2+) | своё приложение на часах обновляет план напрямую |

## 5. Доставка на часы (WorkoutKit)

После каждого применения изменений `WorkoutScheduleReconciler`:
1. Берёт из GRDB тренировки с `execution == workoutkit` на окно «сегодня … +7 дней» (с учётом системного лимита на число запланированных тренировок). Indoor bike сюда не попадает: на станке часы заняты HeartCast (см. §7).
   `schedule(_:at:)` принимает **только дату** (проверено в S1): `DateComponents(year, month, day)` + явный `timeZone` = эффективный пояс даты (иначе дата привяжется к текущему поясу устройства). Время не передаём. Лимит запланированных — 50.
2. Строит желаемое состояние: `WorkoutPlan` с **id, выведенным из содержимого** — UUID от `sha256(plannedWorkoutId | дата | sha256 записи)`. Запись включает `resolved`, поэтому любая правка плана или порогов даёт новый id. Отдельная таблица соответствий не нужна.
3. Читает фактическое: `WorkoutScheduler.shared.scheduledWorkouts` (только наши).
4. Удаляет наши незавершённые, которых нет в желаемом (удалённые, перенесённые, изменённые, выполненные, пропущенные, ушедшие в прошлое), добавляет недостающие (`schedule(_:at:)`). Завершённые не трогает.
5. Пишет результат в `sync_state.watch` (какие тренировки на часах, ошибка, предупреждения маппинга) — экраны показывают «На часах» / «Ещё не на часах» — и кладёт в outbox отчёт для сервера (`POST /v1/deliveries`), откуда его видит тренер.

Код: `Zone2Kit/WatchDelivery.swift` (маппинг, отбор, сверка — тесты на macOS через `swift test` с фейковым планировщиком), `App/Services/WatchSync.swift` (авторизация WorkoutKit и запуск после каждого pull).

Маппинг структуры в WorkoutKit (`CustomWorkout`: первый шаг-разминка → `warmup`, последний шаг-заминка → `cooldown`, остальное — `IntervalBlock` (повтор → `iterations`); goals time/distance/open; один алерт на шаг по главному таргету: пульс, мощность, каденс, темп → скорость; RPE — именем шага) — чистая функция `WorkoutBridge`, покрытая тестами. Чего WorkoutKit не умеет — например, повторы внутри повторов или шаг «до Lap» в некоторых видах спорта — приводится к ближайшему эквиваленту с предупреждением, которое сервер видит через `delivery_ack.detail`.

## 6. Тренировка → сервер

0. Чтение — через `HKAnchoredObjectQuery` (якорь хранится в GRDB): он отдаёт и новые, и **удалённые** объекты.
1. Observer видит новый `HKWorkout` (от любого источника; свой раннер в ф.2 тоже пишет в HealthKit).
2. `HealthBridge.export(workout)` собирает **дамп без потерь**: метаданные, `workoutActivities` (мультиспорт), события (lap, segment, pause), все связанные сэмплы (пульс, дистанция, скорость, мощность, каденс, GCT, VO, длина шага, мощность бега, гребки, калории), маршрут (`HKWorkoutRoute` → все точки), устройство и источник.
3. gzip → outbox `activity_upload`.
4. Сервер (`ingest/healthkit`): валидация → `streams` 1 Гц (+ GAP) → laps → погода из метаданных (°F → °C, влажность через `HKUnit.percent()`) → привязка к тренировке плана (по дате и виду спорта; шаги не сопоставляются, D41; только при загрузке — задним числом связывает MCP `link_activities`) → зоны и нагрузка → ровные участки (Pw:HR, декаплинг, тренд эффективности) → трасса → обувь по умолчанию → **генерация FIT** → файлы в Storage → запись в ленту синка (активность появляется на телефоне уже с разбором).

### 6.1 Удаления из Health
`deletedObjects` из anchored query → outbox `health_deleted` → сервер находит активность по источнику: если это её единственный источник — мягко удаляет (`deleted_at`, `deleted_reason: health_deleted`), если активность склеенная — отцепляет источник и пересчитывает. Tombstone уходит в ленту синка. Типичный сценарий: атлет удаляет из Health запись HeartCast со станка, а observer уже успел её отправить.

### 6.2 Бэкфилл
При первом запуске — **вся история HealthKit** (не «последние N месяцев»): тренировки — от новых к старым, фоном (`BGProcessingTask`), с прогрессом на экране Debug. Для старых тренировок FIT заранее не генерируется (по запросу).

## 7. MyWhoosh → сервер → Health

> **Заморожено (D48, 2026-11-20).** Станок переходит на своё приложение ([11-trainer](11-trainer.md)): заезд пишется в Health нашими часами и приходит на сервер обычным экспортом (§6). `intervals-poll` и запись заездов MyWhoosh в Health не делаем; ручной импорт FIT (ниже) остаётся.

Как реально устроен станок: пульс с часов идёт через **HeartCast** в MyWhoosh, поэтому **FIT MyWhoosh уже содержит пульс** (и мощность, каденс). Запись, которую HeartCast оставляет в Health, атлет удаляет. Часы на станке заняты HeartCast — тренировку WorkoutKit для indoor bike не ставим.

1. Job `intervals-poll` (pg_cron, каждые 15 минут): `GET /api/v1/athlete/{id}/activities?oldest=<cursor>` → новые заезды → скачивание **оригинального файла** → `fit_original`.
2. **Основной путь:** `ingest/fit` → activity целиком из FIT (пульс, мощность, каденс) → `health_export: pending` → приложение пишет `HKWorkout` (indoor cycling) с мощностью, каденсом, пульсом, дистанцией и калориями, `HKMetadataKeyExternalUUID` = наш id → `health_written`.
2a. **Strava тоже пишет заезды MyWhoosh в Health** (S1: HK-запись с `source = Strava`, `HKIndoorWorkout`), но с потерей деталей. Источник истины — **только FIT из intervals.icu** (D33). HK-запись от Strava сервер помечает как дубль заезда (по пересечению времени) и данные из неё не берёт. Как только приложение пишет заезды в Health само (фаза 1), запись Strava → Health отключается в настройках Strava, чтобы в Health не было двух экземпляров.
3. **Запасной путь — склейка:** если в HealthKit осталась пересекающаяся по времени (>50%) запись с часов (не удалили / писали тренировку на часах), объединяем в `merged`: мощность и каденс из FIT, пульс — из лучшего источника; запись в Health не дублируем (`skipped_overlap`). Если атлет потом удалит запись часов из Health — §6.1 отцепит источник, и сервер переключит активность на основной путь (запишет её в Health сам).
4. Дедупликация по `externalId` intervals.icu и по пересечению времени.

**Ручной путь (сейчас, до intervals-poll):** атлет выгружает FIT из MyWhoosh. Тренер в чате вызывает `create_upload_link`, и атлет загружает файл на одноразовой странице `/u/:token` (1 час, одно использование, файл сразу проверяется). Затем `import_activity_file({uploadId})` — других способов передать файл нет. `ingest/fit`: FIT конвертируется в форму дампа HealthKit (`domain/fit.ts`), дальше общий `saveDump`: summary, круги (круги FIT становятся `segment`, длины бассейна — `lap` с гребками и стилем), дедупликация (FIT — лучший источник: копия Strava помечается дублем, связь с планом переходит к FIT), привязка к плану. Оригинал хранится байт в байт как `fit_original`; ряды и пересчёт summary декодируются из него по запросу. `sourceId` = sha256 файла, поэтому повторный импорт идемпотентен. Особенности реального FIT MyWhoosh (`fixtures/fit/mywhoosh-2026-11-13.fit`): координаты — виртуальный мир приложения, для indoor маршрут не сохраняется; время в движении считается по виртуальной скорости (≥ 1 м/с), поэтому стоянка до старта не входит; каденс без нулей (у самого файла `avgCadence` их включает); весь заезд — один круг, поэтому `segment` нет. Запись заезда в Health приложением (`health_export`) пока не сделана.

## 7a. Часовые пояса на устройстве
Устройство передаёт текущий пояс при каждом синке (`devices.timezone`). Дата «сегодня» на экране Today и время тренировок на часах — в эффективном поясе даты ([03 §1.1](03-data-model.md#11-часовые-пояса)), который сервер отдаёт в профиле (дом + поездки).

## 8. Метрики восстановления

Реализовано (`ios/App/Health/DailyMetricsSync.swift`, агрегация — `Zone2Kit/DailyMetrics.swift`, сервер — `POST /v1/daily-metrics`).

- **Когда:** при каждом синке и pull (foreground, pull-to-refresh, фоновое пробуждение) и по observer'у сна (`sleepAnalysis`, background delivery раз в час). Первый запуск — **бэкфилл за год** (база для сравнения), дальше — **последние 8 дней** каждый раз: поздняя досинхронизация с часов заменяет день целиком. Outbox: `daily-metrics-backfill` и `daily-metrics` — разные id, чтобы недельное обновление не затёрло ещё не отправленный бэкфилл.
- **Что за день (локальная дата телефона):** пульс покоя — последний сэмпл дня; HRV SDNN — среднее сэмплов дня и их число; частота дыхания и температура запястья во сне — к дате **пробуждения** (по концу сэмпла); вес и VO2max — последний за день.
- **Сон:** сэмплы `sleepAnalysis` по источнику → сессии (разрыв > 3 ч — новая сессия) → дата пробуждения; если ночь записали несколько приложений, берётся один источник с наибольшим временем сна (без двойного счёта). Минуты сна = core + deep + REM + «asleep»; `awake` отдельно; `inBedStart/End` — границы сессии.
- **Разрешения:** новые типы (частота дыхания, температура запястья) запрашиваются отдельным листом, только когда приложение на экране.
- **Сервер:** день заменяется целиком (`upsert` по `(user_id, date)`); MCP `get_daily_metrics` сравнивает с базой атлета (28 дней до даты, нужно ≥14 значений) и ставит флаги, `get_context.recovery` — последние 3 дня. В ленту синка метрики не идут: на телефоне они и так есть в Health.

## 9. Состояние «доставлено» в UI

Экран Today показывает строку состояния: `Updated 18:02 · On watch ✓` / `Updated 9 h ago — open with network to refresh` / `Not on watch: <причина>`. Те же данные AI видит через `get_delivery_status`.
